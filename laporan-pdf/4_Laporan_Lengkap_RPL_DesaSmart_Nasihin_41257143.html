BAB I: PRODUCT REQUIREMENTS DOCUMENT (PRD / SRS MANDIRI)

1.1 Identifikasi Masalah & Latar Belakang Nyata

Pelayanan publik di tingkat desa di Indonesia menghadapi tantangan besar terkait efisiensi dan transparansi administrasi. Surat Keterangan Tidak Mampu (SKTM) merupakan dokumen fundamental yang menjadi prasyarat pokok bagi warga berpenghasilan rendah untuk memperoleh jaminan kesehatan gratis (PBI BPJS), beasiswa pendidikan, santunan sosial, serta pembebasan biaya administrasi lainnya. Namun, prosedur manual konvensional yang berjalan di kantor balai desa kerap membebani warga dengan antrean fisik panjang, keharusan bolak-balik akibat ketidaklengkapan dokumen pengantar RT/RW, dan keterbatasan jam operasional loket.

Dari sisi aparatur desa, petugas loket dan Kepala Seksi (Kasi) Pelayanan menghadapi kendala dalam memvalidasi keabsahan data ekonomi keluarga secara objektif. Pemeriksaan berkas fisik secara manual rentan terhadap ketidaktelitian dan memakan waktu berhari-hari. Selain itu, dokumen fisik berbasis kertas mudah dipalsukan, stempel basah mudah ditiru, serta menyulitkan instansi luar (sekolah, dinas sosial, dan perbankan) dalam mengonfirmasi keaslian dokumen secara cepat.

Menjawab urgensi tersebut, penulis merancang dan membangun sistem Desa Smart, yakni platform aplikasi web modern yang mendigitalkan siklus pelayanan SKTM secara menyeluruh dengan menanamkan modul Kecerdasan Artifisial (Artificial Intelligence) untuk otomatisasi asistensi warga, validasi kelayakan ekonomi, tanda tangan elektronik (TTE) berbasis QR Code terenkripsi SHA-256, dan notifikasi WhatsApp instan.

1.2 Nilai Guna Aplikasi & Tujuan Rekayasa

Tujuan utama rekayasa perangkat lunak mandiri ini adalah menghasilkan sistem informasi pelayanan publik terpadu yang memberikan manfaat strategis:

  • Efisiensi dan Aksesibilitas 24/7: Masyarakat dapat berkonsultasi mengenai syarat layanan melalui asisten cerdas AI, mengajukan permohonan SKTM, serta melacak progres berkas kapan saja dan di mana saja tanpa terhambat jam buka balai desa.
  • Asesmen Objektif & Terstandarisasi Berbasis AI: Menggunakan modul inferensi LLM untuk menganalisis data penghasilan bulanan, jumlah tanggungan keluarga, kondisi hunian, serta pencocokan konsistensi NIK berkas KTP/KK secara otomatis (AI Completeness Score).
  • Akuntabilitas Birokrasi Berjenjang: Rantai verifikasi berjenjang: verifikasi berkas oleh Staf Loket → validasi substantif kemiskinan dan data DTKS oleh Kasi Pelayanan → pengesahan tanda tangan elektronik oleh Kepala Desa.
  • Integritas Dokumen & Pencegahan Pemalsuan: Dokumen SKTM resmi diterbitkan dalam format PDF ber-Kop Desa dengan nomor registrasi unik, disematkan TTE ber-QR Code, dan diamankan dengan algoritma Cryptographic Hash SHA-256 yang dapat divalidasi langsung oleh pihak luar melalui portal verifikasi terbuka tanpa login.

1.4 Spesifikasi Kebutuhan Non-Fungsional

  • Keamanan (Security): Seluruh kata sandi di-hash dengan bcrypt (10 salt rounds). Sesi otentikasi menggunakan cookie JWT HttpOnly & SameSite. Dokumen SKTM dilindungi tanda tangan digital dengan algoritma SHA-256 cryptographic digest.
  • Performa (Performance): Navigasi halaman responsif < 500ms (Next.js Server Components). Inferensi AI Groq < 1,5 detik. Pembuatan berkas PDF TTE < 800ms.
  • Ketersediaan (Availability): Sistem beroperasi 24/7 dengan mekanisme safe-fallback jika API pihak ketiga mengalami kendala jaringan.
  • Auditabilitas (Auditability): Seluruh mutasi data dicatat ke tabel audit_logs lengkap dengan IP, user agent, dan timestamp.

1.5 Spesifikasi Strategis Fitur Kecerdasan Artifisial (AI Engine)

Fitur AI terintegrasi pada dua pilar fungsional:

  1. Conversational Chatbot AI: Menggunakan Groq Cloud LLM (Llama-3-70B / DeepSeek-R1) dengan system prompt context regulasi Desa Silihasih, daftar wilayah 5 RW/12 RT, jam pelayanan balai desa, kriteria penerima SKTM, dan panduan upload berkas.
  2. Asesmen Kelayakan & OCR Matching: AI mengevaluasi kriteria kemiskinan (penghasilan vs tanggungan keluarga), menghasilkan AI Completeness Score (0-100), dan mencocokkan konsistensi NIK/Nama formulir dengan data dokumen lampiran.

2.2 Penjelasan Titik Keputusan (Decision Points) & AI Pipeline

  • Titik Keputusan AI Engine (Koneksi AI): Jika koneksi ke Groq API berjalan normal, sistem menghitung Completeness Score dan mencocokkan OCR identitas. Jika terjadi kendala jaringan/timeout, sistem menerapkan safe-fallback skor default 100 status UNCHECKED sehingga berkas warga tetap aman tersimpan untuk diperiksa manual oleh staf.
  • Titik Keputusan Staf Loket (Validasi Administratif): Staf memeriksa keabsahan fisik berkas. Bila dokumen buram atau salah unggah, staf memilih NEED_REVISION yang memicu notifikasi WhatsApp ke pemohon untuk mengunggah ulang berkas perbaikan tanpa perlu mengulang form dari awal. Bila lengkap, staf mendisposisikan ke Kasi Pelayanan (SUPERADMIN_REVIEW).
  • Titik Keputusan Kasi Pelayanan (Validasi Substantif Kemiskinan): Kasi melakukan uji substansi: apakah pemohon benar-benar memenuhi kriteria warga tidak mampu berdasarkan basis data kemiskinan (DTKS). Jika tidak layak, Kasi menolak permohonan (REJECTED). Jika layak, diteruskan ke Kepala Desa (HEAD_REVIEW).
  • Titik Keputusan Kepala Desa (Pengesahan Yuridis & TTE): Persetujuan Kades memicu penomoran otomatis registrasi desa, pembentukan QR Code TTE verifikasi terbuka, kalkulasi cryptographic hash SHA-256, dan perenderan PDF resmi.
  • Alur Terminasi Sesi (Logout): Seluruh aktor yang telah selesai bertugas dapat menekan tombol Logout untuk mengakhiri sesi, membersihkan cookie otentikasi JWT, dan mencatat log audit sistem.

3. CLASS DIAGRAM BERORIENTASI OBJEK (MEMATUHI PRINSIP SOLID)

3.1 Penerapan 5 Prinsip SOLID dalam Arsitektur

  • Single Responsibility Principle (SRP): Setiap modul memiliki tanggung jawab tunggal. AuthService hanya mengelola login, register, OTP, dan logout; ApplicationService mengelola alur status SKTM; GroqAiService khusus menangani inferensi LLM; WhatsAppGateway khusus mendistribusikan pesan notifikasi; dan JsPdfGeneratorService khusus memproduksi dokumen PDF.
  • Open/Closed Principle (OCP): Arsitektur terbuka untuk penambahan provider komunikasi baru (misal: SMS Gateway) cukup mengimplementasikan antarmuka INotificationSender tanpa merombak logika inti ApplicationService.
  • Liskov Substitution Principle (LSP): Objek kelas turunan WhatsAppGateway dan EmailGateway dapat saling menggantikan antarmuka INotificationSender secara mulus.
  • Interface Segregation Principle (ISP): Antarmuka dipisahkan secara spesifik dan ramping: IAuthService, IApplicationService, IAiService, INotificationSender, dan IPdfGenerator.
  • Dependency Inversion Principle (DIP): Modul tingkat tinggi (Controller / Route Handlers) bergantung pada abstraksi interface, bukan pada modul tingkat rendah secara langsung.

8API → Fonnte WA APIHTTP POST api.fonnte.com/send mengirimkan notifikasi pesan konfirmasi pengajuan ke nomor WhatsApp warga.
9API → React UIMerespons HTTP 201 Created membawa applicationId.
10React UI → PemohonMenampilkan notifikasi sukses di layar dan me-redirect browser ke dashboard warga.

4.2 Sequence 2: Approval Kepala Desa, TTE QR Code & Hash SHA-256

  1. Kepala Desa membuka dashboard dan mengklik *Setujui & Terbitkan SKTM*.
  2. UI mengirimkan HTTP PATCH ke /api/applications/[id]/review dengan aksi HEAD_APPROVE.
  3. API memvalidasi wewenang peran Kepala Desa dan mengambil data lengkap pemohon dari Prisma DB.
  4. API men-generate nomor surat urut resmi: 470/xxx/SKTM/Desa/2026.
  5. API menyusun URL verifikasi publik dan memanggil JsPdfGeneratorService.
  6. Layanan PDF membangkitkan gambar QR Code TTE dan menghitung cryptographic digest SHA-256 dokumen.
  7. Layanan PDF merender halaman berkop resmi lengkap dengan QR Code dan mengembalikan buffer dokumen.
  8. API mengeksekusi transaksi Prisma untuk mengubah status menjadi COMPLETED, menyimpan record generated_documents, dan mencatat audit log HEAD_APPROVE.
  9. API memicu pengiriman pesan WhatsApp ke pemohon berisi tautan unduhan dokumen asli.
  10. Kepala Desa menerima notifikasi sukses dan pratinjau dokumen terbit.

4.3 Sequence 3: Alur Logout Akun & Terminasi Sesi (Fitur Baru)

  1. Pengguna (Warga, Staf, Kasi, Kades) mengklik tombol *Keluar (Logout)* pada Header atau Sidebar.
  2. UI mengirimkan request HTTP POST ke /api/auth/logout dengan menyertakan cookie otentikasi.
  3. API membaca identitas pengguna aktif dan menulis entri audit log action: 'LOGOUT' ke basis data.
  4. API menghapus cookie desasmart_session.
  5. API merespons status 200 OK { success: true, message: 'Berhasil logout.' }.
  6. UI melakukan redirect browser ke rute login publik /login.
